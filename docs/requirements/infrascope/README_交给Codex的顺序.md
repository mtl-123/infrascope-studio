# InfraScope 需求与研发执行包

这是一份完整需求基线和执行约束，不是“全部功能已开发完成”的声明。

建议使用顺序：

1. 将本包完整放入原项目 docs/requirements/infrascope/，保留 source/RDP原始需求.md。
2. 先看 01_完整产品需求PRD.md 确认产品范围；其编号是后续追踪主键。
3. 同时向 Codex 提供整个包，复制 04_Codex执行提示词.md 的“主提示词”，让它在当前项目实施。
4. 按 03_阶段开发与闭环验收.md 的 P0–P12 检查阶段交付，不要只看最终截图。
5. 每次让 Codex 更新 05_需求追踪矩阵.csv，保留代码位置、实际测试与证据。全部状态初始待核对，不能用本包直接报通过。
6. 发生上下文切换时使用提示词中的续接段，继续原项目与矩阵，不重复建站。

| 文件 | 作用 |
|---|---|
| 01_完整产品需求PRD.md | 全模块范围、前后端/客户端分工、功能与验收条件、状态和目标 |
| 02_架构与接口契约.md | Go/Rust/PG/两类客户端、数据准确性、可靠性、模型/API、容量和部署 |
| 03_阶段开发与闭环验收.md | 13 个阶段、逐需求测试规范、70 个系统闭环场景、真实环境与门禁 |
| 04_Codex执行提示词.md | 完整执行、续接开发、仅评审三种可复制提示词 |
| 05_需求追踪矩阵.csv | 编号、来源、阶段、责任层、测试、实现/证据/阻塞的可更新清单 |
| 06_原始诉求与附件映射.md | 对话全部诉求、附件 0–35 的保留与冲突裁决 |
| 07_附件逐条核对清单.csv | 原附件每个有内容段落/列表/表格/代码块的逐条阅读核对 |
| 08_文档覆盖检查.md | 本包生成时的机械覆盖与一致性检查；不是软件测试报告 |
| source/RDP原始需求.md | 原始附件完整字节保留，任何摘要都不能取代它 |

阶段门禁减少返工：先在原项目确认关键交互和契约，再做真实纵向链路。已确认的设计和现有可复用代码不用重复审批或重写。

真实环境条件应尽早准备：Windows 与 Linux 测试机、两个 Windows 交互桌面、原生 PostgreSQL、声明支持的设备型号、浏览器，以及明确授权的企业微信/邮件测试通道。不要把生产密码写进文档或聊天。

本包没有自动增加生产操作权限，也没有调用通知发送、远程接入或更改当前应用。它用于你交给 Codex 后有依据地开发、检查和验收。
